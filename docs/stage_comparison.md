# PropCare AI: architecture progression

PropCare AI solves the same tenant-operations problem at three increasing levels of capability. Keeping the stages side by side makes the trade-off visible: each stage is useful, but each leaves a different amount of coordination to the application.

| Stage | What changed | Why it is useful |
| --- | --- | --- |
| **Stage 1 — LangChain** | One general-purpose LangChain `create_agent()` selects from tenant, unit, rent, maintenance-history, and work-order tools. It returns a Pydantic `TenantResolution` and uses built-in PII middleware. | This is a compact fit for a simple, single-request support desk. The agent can answer “Has my rent been paid?” or create a straightforward work order without application-managed specialist routing. |
| **Stage 2 — LangGraph** | The single agent becomes an explicit `StateGraph` with a Supervisor and Maintenance, Billing, and Resident Services specialists. State carries the tenant, issue, request, credit, status, and resolution. Specialists return to the Supervisor, creating a genuine cycle. A checkpointer and `thread_id` preserve workflow state, while raw `interrupt()` and `Command(resume=...)` implement human approval. | This adds reliable control over multi-step work. For example, a recurring heater failure can go Maintenance → Supervisor → Billing → Supervisor, then pause for a manager instead of allowing an AI to approve money. The trade-off is more hand-written state, nodes, edges, and routing logic. |
| **Stage 3 — Deep Agents** | A Deep Agent coordinator delegates to named subagents using `subagents=`. Each specialist has its own focused instructions and tool set; shared operating rules come from `AGENTS.md`. The coordinator returns `Stage3Resolution` rather than an unstructured response. | This reduces the amount of manual orchestration needed for broader, multi-domain operations while preserving safe tool boundaries and structured results. It is a better abstraction when the coordinator needs to plan, delegate, and synthesise several specialist findings. |

The old code could not simply remain unchanged because the requirements change with the workflow. A Stage 1 single agent does not provide explicit supervisor-to-specialist cycles or pause/resume semantics. A Stage 2 graph deliberately models those controls, but its fixed nodes and conditional edges become increasingly verbose as independent specialist contexts and broader planning are added. Stage 3 therefore introduces the Deep Agents coordinator and subagent abstraction, while retaining the same tenant-safe services, structured domain data, approval boundary, and frontend experience.

This is not a claim that one stage replaces all others universally. Stage 1 remains the clearest teaching example for a focused support task. Stage 2 is the most transparent representation of graph state and human-in-the-loop control. Stage 3 is the most suitable demonstration of delegated property operations. Together they show increasing architectural capability applied to one consistent PropCare domain.
